# حالت MQTT — برنامهٔ کاملاً استاتیک

در این حالت **هیچ سروری وجود ندارد**. کل بک‌اند داخل مرورگر است
(`static/js/mqtt-backend.js`) و روی MQTT-over-WebSocket به یک بروکر وصل می‌شود.
به همین دلیل صفحه را می‌شود روی **GitHub Pages** گذاشت.

```
مرورگر کاربر A ──┐
                 ├── MQTT over WebSocket ──→ بروکر (EMQX / HiveMQ / Mosquitto)
مرورگر کاربر B ──┘        pub/sub + retained
```

هیچ دیتابیس، دیسک یا آپلودی در کار نیست؛ «ذخیره‌سازی» همان پیام‌های
**retained** بروکر است.

---

## سه نوع پیام

| نوع | کاربرد | مثال |
|---|---|---|
| **retained** | state — آخرین مقدار هر تاپیک، پس کاربر تازه هم فوراً همه‌چیز را می‌گیرد | کاربران، پست‌ها، گروه‌ها، لایک‌ها، استوری‌ها |
| **غیر retained** | رویداد لحظه‌ای — جایگزین Socket.IO | پیام چت، تایپینگ، سیگنال WebRTC، اعلان |
| **retained + Last Will** | حضور — با بسته‌شدن مرورگر، خودِ بروکر آفلاین را منتشر می‌کند | `presence/<uid>` |

«حذف» در MQTT یعنی انتشار **payload خالی** روی همان تاپیک.

## نقشهٔ تاپیک‌ها

پیشوند همهٔ تاپیک‌ها `jvl/<networkKey>/v1` است تا دو گروه روی یک بروکر عمومی
قاطی نشوند (کلید پیش‌فرض: `volexturn4`).

### state (retained)

| تاپیک | محتوا |
|---|---|
| `user/<uid>` | پروفایل کاربر (نام، بیو، آواتار، نقش، هش رمز) |
| `uname/<username>` | نگاشت نام‌کاربری → شناسه (برای ورود) |
| `presence/<uid>` | `{online, at, name}` + Last Will |
| `group/<gid>` | مشخصات گروه |
| `member/<gid>/<uid>` | عضویت و نقش |
| `post/<pid>` | پست (متن + رسانه به‌صورت data URL) |
| `like/<pid>/<uid>` | لایک (بودن تاپیک = لایک شده) |
| `view/<pid>/<uid>` | بازدید یکتا به ازای هر کاربر |
| `cmt/<pid>/<cid>` | کامنت |
| `story/<sid>` | استوری + `expires_at` |
| `sview/<sid>/<uid>` | بینندهٔ استوری |
| `follow/<follower>/<followee>` | دنبال‌کردن |
| `lan/<hid>` | سرور بازی شبکهٔ محلی |
| `pin/<scope>` | پیام سنجاق‌شدهٔ هر گفتگو |
| `ban/<uid>` | بن‌شدن حساب: `{by, reason, at}` — بودن تاپیک = بن بودن |

### رویدادها (غیر retained)

| تاپیک | رویدادها |
|---|---|
| `evt/dm/<uid>` | `msg` · `edit` · `delete` · `seen` · `pin` · `typing` · `clear` |
| `evt/group/<gid>` | همان‌ها برای گفتگوی گروهی |
| `evt/notify/<uid>` | اعلان لایک/کامنت/فالو |
| `evt/voice/<room>` | سیگنال WebRTC (offer/answer/ICE) |
| `evt/global` | `post_like` · `post_comment` · `post_view` · `follow_update` · `groups_changed` · `post_deleted` · `message_deleted` |

هر کلاینت یک‌بار `jvl/<key>/v1/#` را subscribe می‌کند؛ هم state از retainedها
ساخته می‌شود و هم رویدادها می‌رسند.

## تشخیص خودکار حالت

`index.html` همیشه لایهٔ MQTT را بارگذاری می‌کند. لایه، اول `api/app_info` را
با `fetch` اصلی صدا می‌زند:

- اگر **سرور نود** پشت همان آدرس بود (پاسخ بدون فیلد `transport`) → همهٔ
  درخواست‌ها به سرور واقعی واگذار می‌شود و `socket.io.min.js` بارگذاری می‌شود.
- اگر نبود (مثلاً روی Pages) → **حالت MQTT** فعال می‌شود.

پس یک `index.html` هم روی Pages کار می‌کند هم روی سرور محلی، بدون تغییر.

مسیر رسانه هم از `mediaURL(kind, value)` رد می‌شود: در حالت MQTT یک
`data:` URL برمی‌گرداند و در حالت REST همان `/files/<kind>/<name>`.

## تنظیم بروکر و کلید شبکه

```js
JVL.setBroker('wss://broker.hivemq.com:8884/mqtt');  // تغییر بروکر
JVL.setNetworkKey('khdodemon');                      // شبکهٔ اختصاصی خودت
JVL.state.ready();                                   // وضعیت اتصال
JVL.mode();                                          // 'mqtt' یا 'rest'
```

یا مستقیم در localStorage: `jvl_broker` و `jvl_network`.

بروکرهای عمومی آماده:

| بروکر | آدرس WebSocket |
|---|---|
| EMQX (پیش‌فرض) | `wss://broker.emqx.io:8084/mqtt` |
| HiveMQ | `wss://broker.hivemq.com:8884/mqtt` |
| Mosquitto | `wss://test.mosquitto.org:8081/mqtt` |

## محدودیت‌های این حالت (مهم)

1. **بدون امنیت واقعی.** روی بروکر عمومی هر کسی می‌تواند تاپیک‌ها را
   subscribe کند. هش رمز هم قابل خواندن است. ورود/ثبت‌نام فقط برای جلوگیری
   از ورود تصادفی است. برای استفادهٔ جدی، بروکر خصوصی با TLS و ACL بگذار.
2. **تاریخچهٔ چت ماندگار نیست.** پیام‌ها غیر retained هستند (وگرنه بروکر عمومی
   زیر بار می‌رفت)، پس هر مرورگر فقط پیام‌های همان نشست را نگه می‌دارد.
   با رفرش، چت خالی می‌شود — ولی کاربران، پست‌ها، استوری‌ها، گروه‌ها، لایک‌ها
   و فالوها (همه retained) سر جایشان می‌مانند.
3. **رسانه موقتی است و سقف دارد** (جدول زیر). ویدیو فقط در چت، چون تکه‌تکه و
   غیر retained می‌رود؛ استوری و پست retained هستند و فقط عکس می‌گیرند.
4. **«اولین کاربر = مدیر» رقابتی است.** اگر دو نفر هم‌زمان ثبت‌نام کنند ممکن
   است هر دو مدیر شوند. بعداً از پنل مدیریت قابل اصلاح است.
5. **شمار بازدید/لایک با تأخیر همگام می‌شود** (در حد چند صد میلی‌ثانیه).
6. استوری‌های منقضی توسط خودِ کلاینت‌ها فیلتر می‌شوند؛ تا وقتی کسی صفحه را باز
   نکند، تاپیکشان روی بروکر می‌ماند.

## رسانهٔ موقتی (آپلود بدون سرور)

هیچ دیسکی در کار نیست؛ رسانه به `data:` URL تبدیل می‌شود و از همان تاپیک‌های
MQTT می‌رود. دو مسیر دارد:

| مسیر | برای | چطور | سقف |
|---|---|---|---|
| **تک‌پیام** | عکس، صوت کوتاه، آواتار، استوری، پست | عکس با نردبان فشرده‌سازی (۱۲۸۰→۳۸۰px، کیفیت ۰٫۷→۰٫۴) کوچک می‌شود و داخل همان پیام می‌نشیند | ~۷۰۰KB متن |
| **تکه‌تکه** | ویدیو و فایل بزرگ **فقط در چت** | به تکه‌های ۱۲۰KB بریده و روی `evt/dm/<uid>` یا `evt/group/<gid>` با `t:'chunk'` فرستاده می‌شود؛ گیرنده بازسازی می‌کند | ۱۰MB |

نکته‌های پیاده‌سازی:

- پیام **اول** می‌رسد با `file_path: "media:<id>"` و جای خالی رسانه («در حال
  دریافت…»)؛ بعد تکه‌ها یکی‌یکی می‌رسند و وقتی کامل شد رویداد `message_updated`
  گفتگو را دوباره رندر می‌کند.
- تکه‌ها **غیر retained** هستند، یعنی واقعاً موقتی: فقط به گیرندهٔ همان لحظه
  می‌رسند و جایی ذخیره نمی‌شوند. به همین دلیل ویدیو در استوری/پست ممکن نیست —
  آن‌ها retained‌اند و باید بعداً هم قابل خواندن باشند.
- انتقال نیمه‌تمام بعد از ۱۲۰ ثانیه دور ریخته می‌شود و کش رسانه حداکثر ۶۰
  مورد نگه می‌دارد تا حافظهٔ مرورگر پر نشود.
- پیشرفت ارسال و دریافت با قرص پایین صفحه (`upload_progress` / `download_progress`)
  نشان داده می‌شود.
- سقف‌ها در `Config` هستند: `mediaLimit` (۷۰۰KB)، `chunkText` (۱۲۰KB)،
  `streamLimit` (۱۰MB). از طریق `GET /api/app_info` هم اعلام می‌شوند.

> بروکرهای عمومی معمولاً ~۱MB سقف بسته دارند؛ اگر بروکر خصوصی با سقف بالاتر
> داری، `chunkText` را بالا ببر تا انتقال سریع‌تر شود.

## دیپلوی روی GitHub Pages

Pages این مخزن روی شاخهٔ جاری و مسیر `/` تنظیم شده، پس **هر push یعنی دیپلوی**:

```bash
git push origin arena/ac24cb6b-jvl-platform
# چند ثانیه بعد:  https://javadxpro.github.io/JVL.PLATFORM/
```

چون همهٔ مسیرهای `index.html` نسبی هستند، زیردامنهٔ `/JVL.PLATFORM/` مشکلی
ایجاد نمی‌کند (لایهٔ MQTT هم این پیشوند را از مسیرهای API حذف می‌کند).

اگر خواستی روی `main` منتشر شود، منبع Pages را در
`Settings → Pages → Source` به `main / (root)` تغییر بده.

## تماس (WebRTC یک‌به‌یک)

سیگنال روی تاپیک غیر retained `evt/call/<uid>` می‌رود و رسانه **P2P** است.
هیچ سرور رسانه‌ای در کار نیست.

| پیام | جهت |
|---|---|
| `{t:'offer', callId, video, from, fromName}` | تماس‌گیرنده → مخاطب |
| `{t:'accept'}` | پاسخ‌دهنده → تماس‌گیرنده |
| `{t:'signal', sdp\|ice}` | دوطرفه؛ پیشنهاد (offer) همیشه از تماس‌گیرنده است |
| `{t:'reject'}` / `{t:'end'}` | قطع تماس |

ICE: سه STUN عمومی (Google ×۲، Cloudflare). اگر NAT طرفین متقارن باشد وصل نمی‌شود؛
آن‌وقت `localStorage['jvl_turn']` را با `{"urls":"turn:…","username":"…","credential":"…"}`
پر کن.

## بن‌کردن در حالت MQTT

تاپیک retained: `ban/<uid>` → `{by, reason, at}`

با انتشار این تاپیک، نشست کاربر همان لحظه از کار می‌افتد: `needAuth` هر درخواستش
را با ۴۰۳ رد می‌کند، `/login` با رمز درست هم ۴۰۳ می‌دهد (عمداً **بعد** از بررسی
رمز، تا فهرست حساب‌های بن‌شده لو نرود)، و خودِ کلاینت رویداد `banned` را می‌گیرد و
نشستش را پاک می‌کند.

**بنِ نشانی IP در این حالت ممکن نیست.** هیچ سروری بین مرورگر و بروکر عمومی نیست،
پس IP هیچ‌کس دیده نمی‌شود؛ تنها چیزی که مرورگر می‌بیند IP خودش است. مسیر
`POST /api/admin/ban_user/:id` اینجا `banned_ip: null` برمی‌گرداند و در `ip_error`
همین را صادقانه می‌گوید — نه اینکه بی‌صدا وانمود کند نشانی بسته شد. برای بنِ IP
نسخهٔ سرور نود را اجرا کن (`server/ban.js`).

## همسان‌سازی مخاطبین بدون لو رفتن شماره

تاپیک retained: `phone/<hash>` → `{ id, at }`

- نرمال‌سازی: فقط رقم، با پیش‌شمارهٔ کشور (`۰۹۱۲…`/`۰۰۹۸…`/`+۹۸۹۱۲…`/`۹۸۹۱۲…` → `۹۸۹۱۲…`)
- هش: `'p' + SHA-256('jvl-phone:' + رقم‌ها)`، ۲۴ کاراکتر اول
- جست‌وجو فقط روی کشِ محلیِ همین دستگاه انجام می‌شود؛ **شمارهٔ خام منتشر نمی‌شود**


## کانال (Broadcasting)

یک‌طرفه: فقط مالک منتشر می‌کند، بقیه عضو می‌شوند و می‌خوانند.

| تاپیک | نوع | محتوا |
|---|---|---|
| `channel/<cid>` | retained | `{id, name, bio, avatar, owner_id, created_at, public}` |
| `csub/<cid>/<uid>` | retained | عضویت (`{at}`) |
| `cpost/<cid>/<pid>` | retained | `{id, cid, author_id, content, media, file_type, file_name, at}` |
| `cview/<pid>/<uid>` | retained | بازدید — یک بار برای هر کاربر |
| `ccmt/<pid>/<k>` | retained | `{id, pid, cid, user_id, user_name, content, at}` |

مسیرها: `/create_channel`, `/channels`, `/channel_info/:cid`, `/channel_subscribe/:cid`,
`/channel_post/:cid`, `/channel_posts/:cid`, `/channel_view/:pid`, `/channel_comment/:pid`,
`/channel_comments/:pid`, `/channel_delete/:cid`.

قاعده‌ها: فقط مالک (یا مدیر) منتشر و حذف می‌کند؛ مالک نمی‌تواند عضویت خودش را لغو کند
(کانال یتیم می‌شود)؛ حذف کانال پست‌ها، عضویت‌ها، بازدیدها و نظرها را هم می‌برد.
همین API عیناً در سرور نود هم پیاده شده (`server/routes/channels.js`) تا دو حالت واگرا نمانند.

## تیک سه‌حالته

`✓` ارسال → `✓✓` تحویل → `✓✓` آبی خوانده‌شدن.

- **تحویل**: وقتی پیام به دستگاه گیرنده می‌رسد، لایهٔ MQTT خودش یک رسید غیر retained
  `{t:'ack', by, mids:[…]}` به `evt/dm/<فرستنده>` می‌فرستد. گروه‌ها رسید نمی‌گیرند
  (طوفان پیام راه می‌افتاد).
- **خوانده‌شدن**: فقط `/seen_messages/:sender` وضعیت را عوض می‌کند و رسید منتشر می‌کند.

> ⚠️ `GET /messages/:me/:peer` **عمداً** وضعیت خوانده را عوض نمی‌کند. قبلاً بی‌صدا
> `seen` می‌زد و بعد `/seen_messages` چیزی برای اعلام نمی‌دید (`updated:0`)، در نتیجه
> تیک آبی هرگز به فرستنده نمی‌رسید. خواندن فقط کار `/seen_messages` است.

## اعلان روی گوشی

دو لایه دارد و مرزشان مهم است:

**۱. اپ باز یا در پس‌زمینه — بدون سرور.** صفحه با `showNotification` (و اگر نشد
`new Notification`) اعلان را نشان می‌دهد. روی GitHub Pages هم کار می‌کند. کلید
`localStorage['jvl_notify']` + اجازهٔ مرورگر هر دو لازم‌اند. وقتی کاربر دارد همان
گفتگو را نگاه می‌کند اعلان داده نمی‌شود. `tag` per-مخاطب است تا اعلان‌ها تلنبار نشوند.

**۲. اپ کاملاً بسته — فقط با سرور.** مرورگر **نمی‌تواند** مستقیم به سرویس پوش
(FCM/Apple/Mozilla) درخواست بزند: هدرهای `Authorization` و `TTL` درخواست را غیرساده
می‌کنند و preflightِ CORS رد می‌شود. پس فرستندهٔ پوش حتماً باید یک سرویس HTTPS باشد.
در حالت MQTT/Pages این لایه خودبه‌خود خاموش می‌ماند (کلاینت `/push_public_key` را
۴۰۴ می‌گیرد و بی‌صدا رد می‌شود).

`sw.js` هندلر `push` و `notificationclick` دارد؛ کلیک روی اعلان، اپ را focus می‌کند
و با `postMessage({type:'jvl-navigate'})` یا لینک `?peer=<id>` همان گفتگو را باز می‌کند.

> در iOS باید اپ را با **Add to Home Screen** نصب کنی؛ وب‌پوش در سافاریِ بدون نصب
> کار نمی‌کند.

### واردکردن فایل vcf

علاوه بر Contact Picker، می‌شود خروجی دفترچهٔ تلفن گوشی (`.vcf`) را وارد کرد.
پارسر `parseVCF()` در `index.html` هر سه نسخهٔ vCard را می‌خواند:

| نکته | چرا مهم است |
|---|---|
| `QUOTED-PRINTABLE` + `CHARSET=UTF-8` | خروجی اندروید نام فارسی را این‌طور کد می‌کند؛ بدون بازش `=D8=B3…` می‌بینی |
| soft break (`=` در آخر خط) | با fold معمولی فرق دارد: هم `=` و هم شکست خط حذف می‌شوند |
| fold معمولی (RFC 6350) | فقط **یک** کاراکتر فاصله/تب از ابتدای خط بعد حذف می‌شود |
| `FN` → `N` → `ORG` | نام به همین اولویت ساخته می‌شود |
| `TEL;TYPE=…`، `VALUE=uri:tel:…` | هر دو سبک پارامتر (۲.۱ بی‌پارامتر و ۳.۰/۴.۰ با `TYPE=`) |
| `PHOTO`/`LOGO` | نادیده گرفته می‌شوند — base64 چندصد کیلوبایتی |
| `\,` `\;` `\n` `\\` | unescape می‌شوند |

**نام‌های دفترچهٔ تلفن** در `localStorage['jvl_contacts']` نگه داشته می‌شوند و در
فهرست چت‌ها و جست‌وجو اولویت دارند (مثل بقیهٔ پیام‌رسان‌ها: نامی که خودت روی
مخاطب گذاشته‌ای). این نگاشت «نام → شماره» **هرگز منتشر نمی‌شود**؛ روی شبکه فقط
هش شماره می‌رود.
